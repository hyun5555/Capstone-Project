# LangChain 설계와 평가 (6단계)

근거 기반 설명(RAG)을 만드는 LangChain 부분이 어떻게 짜여 있고, 왜 그렇게 짰는지, 그리고 그 성능을 어떻게 재는지 정리한 문서입니다.

## 1. 한눈에 보기

```
등기부 / 건축물대장 JSON
  → 청크 나누기 (chunking)
  → ChromaDB 저장 (OpenAI 임베딩)
  → CaseChunkRetriever (항목별 검색, Document 반환)          [app/services/lc_retriever.py, evidence.py]
  → build_targets / build_payload (항목, 판정, 값, 청크에 별칭 E1.. 부여)   [rag_explain.py]
  → 설명 체인                                                  [explain_chain.py]
       ChatPromptTemplate(system + few-shot + human)
       → ChatOpenAI
       → JsonOutputParser
       → 검증 (normalize_explanations)
       → with_retry (형식이 어긋날 때만)
  → rag_explain 이 별칭을 다시 검증한다
  → output_guard 가 숫자와 권리를 규칙으로 검사한다 (근거에 없는 숫자, 없는 권리, 빠뜨린 권리)
  → 하나라도 실패하면 서버가 만든 기본 문장으로 대체
```

판정(일치, 불일치, 비교불가)과 위험 점수는 서버 규칙이 정합니다. LLM 은 이미 정해진 판정을 쉬운 말로 풀어 쓰고, 어떤 근거를 썼는지 표시하는 일만 합니다. 이 분리가 이 설계의 출발점입니다. LLM 이 점수까지 정하면 같은 서류에 매번 다른 결과가 나오고, 틀렸을 때 원인을 찾기 어렵기 때문입니다.

## 2. 프롬프트 설계

### 2.1 역할 (system 메시지 첫 문단)

- 누구에게 말하는가: 부동산 계약이 처음인 임차인. 그래서 어려운 등기 용어를 그대로 옮기지 않고 쉬운 말로 풀게 합니다.
- 무엇을 하는가: (1) 서버가 정한 판정의 이유를 근거 청크에서 찾아 설명한다, (2) 설명에 쓴 근거를 표시한다. 이 두 가지뿐이라고 못 박았습니다.
- 근거: 역할의 범위를 좁게 정하면 판정을 뒤집거나 위험도를 새로 매기는 행동이 줄어듭니다.

### 2.2 조건 (system 메시지의 번호 목록)

| 번호 | 조건 | 넣은 이유 (막으려는 실패) |
| --- | --- | --- |
| 1 | 판정 고정 | LLM 이 서버 판정을 바꾸거나 위험도를 새로 매김 |
| 2 | 근거 한정 (값과 청크에 있는 사실만) | 청크에 없는 금액, 날짜, 이름, 권리를 지어냄 (환각) |
| 3 | 인용 (쓴 청크의 별칭만 evidence_ids 에) | 근거 없는 설명, 또는 쓰지 않은 청크를 인용 |
| 4 | 말소 (머리말에 '말소됨'이 있는 권리는 유효하지 않음) | 말소된 근저당이나 압류를 현재 유효한 권리로 설명 (가장 위험한 오류) |
| 5 | 개인정보 (마스킹 값을 그대로 두고 추측 금지) | 마스킹된 이름이나 번호를 복원하려는 시도 |
| 6 | 청크 안의 지시문 무시 | 문서 속 문장이 프롬프트를 조종하는 주입 공격 |
| 7 | 문체 (존댓말, 항목당 두 문장, 단정 금지) | 길고 단정적인 법률 자문 투의 답변 |
| 8 | 항목별 지침 (일치, 불일치, 권리사항 각각 무엇을 쓸지) | 판정마다 설명의 내용이 들쭉날쭉함 |

### 2.3 출력 형식

`{"items": [{"field", "explanation", "evidence_ids"}]}` 형태의 JSON 하나만 출력하게 합니다. 항목명을 키로 쓰는 v1 형식은 항목명에 특수문자가 들어가거나 하나가 빠졌을 때 어디가 잘못됐는지 알기 어려웠습니다. 배열 형식은 검증하기 쉽고, 모델이 `field` 값을 요청 목록에서 그대로 베끼게 만듭니다.

### 2.4 예시 (few-shot)

- 소유자명 불일치, 구조 유형 일치, 권리사항(유효 근저당과 말소된 가압류가 함께 있는 경우) 세 개를 한 번의 대화 예시로 넣었습니다.
- 예시는 평가 시나리오와 일부러 겹치지 않는 가상 내용입니다. 예시가 정답을 알려 주면 평가가 부풀려지기 때문입니다.
- 예시의 역할은 형식 고정입니다. 인용 별칭을 어떻게 다는지, 말소된 권리를 어떻게 말하는지, 금액을 어떻게 쓰는지를 보여 줍니다.

### 2.5 프롬프트 버전

| 버전 | 구성 | 목적 |
| --- | --- | --- |
| v1 | 사람 메시지 하나에 규칙과 자료를 함께 넣고 JSON 을 파싱만 함. 검증과 재시도 없음 | 비교 기준선 |
| v2 | 역할과 조건은 system, 예시는 few-shot, 자료는 human 으로 분리. 스키마 검증과 재시도 있음 | 개선안 (기본값) |

`EXPLAIN_PROMPT_VERSION=v1` 로 되돌릴 수 있습니다. v2 는 입력 토큰이 더 많으므로(예시와 조건 때문), 품질 향상이 비용 증가를 정당화하는지는 5절의 평가로 확인해야 합니다.

## 3. 체인 구성

`build_explain_chain(version, llm)` 이 만드는 v2 체인은 다음 단계로 이어집니다.

1. 입력 `{payload, fields}`: rag_explain 이 만든 자료 텍스트와 요청 항목명 목록.
2. `RunnableParallel(parsed=..., inputs=RunnablePassthrough())`: 생성 결과와 원래 입력을 함께 다음 단계로 넘깁니다. 검증 단계가 "어떤 항목을 요청했는지"를 알아야 하기 때문입니다.
3. `ChatPromptTemplate | ChatOpenAI | JsonOutputParser`: 메시지를 만들고, 모델을 호출하고, JSON 으로 파싱합니다.
4. `RunnableLambda(normalize_explanations)`: 요청하지 않은 항목, 빈 설명, 형식이 다른 별칭을 버립니다. 쓸 수 있는 항목이 하나도 없으면 `OutputParserException` 을 냅니다.
5. `.with_retry(OutputParserException 만, 최대 2회)`: 형식이 어긋났을 때만 다시 호출합니다. 네트워크 오류는 `ChatOpenAI(max_retries=2)` 가 따로 처리하므로 두 재시도가 겹치지 않습니다.
6. rag_explain 의 인용 검증: LLM 이 인용한 별칭이 그 항목에 실제로 준 청크인지 확인하고, 아니면 버립니다.
7. 서버 검사 (`output_guard.py`, LangChain 밖의 순수 규칙): 프롬프트로 "지어내지 마세요"라고 부탁하는 것만으로는 막을 수 없으므로 서버가 다시 확인합니다.
   - 설명의 숫자(금액, 연도, 면적)가 그 항목의 값과 근거 청크에 없으면 버립니다. `2억 4천만원`처럼 한글 단위로 쓴 금액도 원 단위로 바꿔 비교합니다.
   - 권리사항 설명이 문서에 없는 권리를 있다고 하거나, 현재 유효한 권리를 빠뜨리거나, 유효한 권리를 말소됐다고 하면 버립니다.
   - 버려진 항목은 서버가 만든 기본 문장(정확하지만 딱딱함)으로 대체하고, 응답의 `guard` 에 사유를 남깁니다. 틀린 설명이 나가는 것보다 기본 문장이 안전합니다.
   - 평가(`evaluation.metrics`)도 같은 함수를 씁니다. 서비스가 거르는 기준과 평가 기준이 같습니다.
8. 호출이 실패하거나 응답이 비면 기본 문장으로 대체합니다. 분석은 멈추지 않습니다.

일부 항목만 빠진 경우는 예외로 보지 않습니다. 빠진 항목만 기본 문장으로 채우는 편이 전체를 다시 호출하는 것보다 싸고 안전합니다.

## 4. 컴포넌트별 사용 여부와 이유

| 컴포넌트 | 사용 | 위치와 이유 |
| --- | --- | --- |
| 프롬프트 (ChatPromptTemplate, FewShotChatMessagePromptTemplate) | 사용 | 역할과 조건, 예시, 자료를 메시지 역할별로 나누기 위해. 조건만 고치는 실험(v1 대 v2)이 쉬워짐 |
| 리트리버 (BaseRetriever 상속 CaseChunkRetriever) | 사용 | 항목별로 청크를 찾는 자리. LangChain 표준 인터페이스라 검색 전략(plain, balanced)을 바꿔도 뒤 단계는 그대로임. 결과는 `Document` (본문과 메타데이터) |
| 문서 (Document) | 사용 | 청크 본문에 doc_type, section, rank_no, chunk_id, distance 를 메타데이터로 붙여 인용과 평가에 씀 |
| 벡터스토어 (ChromaDB) | 사용, 직접 연결 | 기존 `chunk_store.py` 의 ChromaDB 를 그대로 두고 리트리버가 감쌈. LangChain 의 벡터스토어 래퍼를 쓰지 않은 것은 사건(case) 단위 삭제, 문서 종류 필터, cosine 거리 설정을 이미 직접 관리하기 때문 |
| 아웃풋 파서 (JsonOutputParser) | 사용 | LLM 문자열을 JSON 으로 바꾸는 자리. 코드블록으로 감싸 나온 경우도 처리. 그 뒤에 스키마 검증 단계를 붙임 |
| 러너블 (Parallel, Passthrough, Lambda, with_retry) | 사용 | 생성, 검증, 재시도를 하나의 체인으로 이음. 검증 실패를 자동 재시도로 연결 |
| 콜백 (BaseCallbackHandler, UsageRecorder) | 사용 | 호출 수, 토큰, 지연시간을 코드 수정 없이 수집. 평가와 비용 계산에 씀 |
| 메모리 | 사용 안 함 | 한 번 분석하고 끝나는 단발성 작업이라 이전 대화가 없음. 이전 출력을 넣으면 오히려 판정 고정 원칙이 흐려짐. 챗봇 기능이 생기면 그때 도입 |
| 툴, 에이전트 | 사용 안 함 | 점수와 판정을 서버가 결정론적으로 계산해야 하고, 검색도 서버가 미리 해서 넘김. 에이전트가 검색이나 계산을 스스로 고르면 같은 입력에 다른 결과가 나오고 비용 예측이 어려움 |

## 5. 성능 평가 (6단계)

### 5.1 무엇을 바꿔 가며 재는가

- 프롬프트 버전: v1, v2
- 청크 크기: 60, 120, 300, 600 (overlap 은 크기의 15%)
- Top-K: 1, 2, 3, 5
- 검색 전략: plain (거리순 상위 K), balanced (등기부와 건축물대장 청크를 각각 최소 하나 포함), adaptive (balanced 에 항목별 Top-K 적용, 5.6 참고)
- 데이터: `sample_data/scenarios.json` 의 합성 시나리오 7개

### 5.2 측정 지표

정확도 (규칙 기반이며 휴리스틱입니다)

- 검색 재현율: 시나리오 데이터에서 자동으로 만든 정답 그룹(예: 해당 권리가 있는 을구 청크)이 검색 결과에 들어왔는가, 그리고 관련 없는 청크가 얼마나 섞였는가(노이즈)
- 인용 유효율, 근거 연결 비율, 인용 커버리지
- 판정 일관성: 판정이 불일치인데 "일치한다"고 쓰지 않았는가, 불일치에 확인 행동이 있는가
- 권리 재현율: 실제 유효한 권리를 빠뜨리지 않았는가
- 환각 지표: 없는 권리를 있다고 썼는가(phantom), 말소된 권리를 유효로 썼는가(cancelled as active), 근거에 없는 숫자를 썼는가
- 서버 검사 탈락률: LLM 이 답했지만 서버 검사에서 버려진 항목의 비율. 환각 지표는 검사를 통과한 설명만 재므로 0 에 가깝게 나오고, LLM 이 원래 저지른 오류의 크기는 이 값으로 봅니다.

효율

- 호출 수, 입력과 출력 토큰, 지연시간 p50 과 p95, 임베딩 토큰
- 비용: `--input-price` 와 `--output-price`(100만 토큰당)를 직접 입력한 경우에만 계산합니다. 가격을 임의로 가정하지 않습니다.

### 5.3 실행 방법 (backend 폴더에서, 가상환경을 켠 상태로)

```
python -m unittest discover -s tests                   # 먼저 테스트
python -m evaluation --dry-run                          # 가짜 부품으로 배관만 확인 (키와 비용 없음)
python -m evaluation --phase retrieval                  # 청크 크기 x Top-K x 전략(plain, balanced, adaptive). 임베딩만 사용, LLM 호출 없음
python -m evaluation --phase prompt --repeat 3 \
    --chunk-size 600 --strategy adaptive \
    --input-price <입력가격> --output-price <출력가격>    # 프롬프트 v1 대 v2
```

실제 호출 전에 예상 LLM 호출 수를 보여 주고 y/N 으로 확인합니다. 결과는 `eval_results/<실행시각>/` 에 `results.json` 과 `report.md` 로 저장됩니다.

### 5.4 결과를 읽을 때 주의할 점

- `--dry-run` 결과는 가짜 임베딩과 가짜 LLM 이라 성능을 뜻하지 않습니다. 배관 확인용입니다.
- 현재 합성 문서는 짧아서 청크 크기 300 이상은 결과가 같게 나옵니다. 청크 크기의 영향을 보려면 60과 120 구간이 의미가 있습니다. 실제 문서 길이의 데이터가 생기면 다시 재야 합니다.
- temperature 가 1 로 고정된 모델이라 출력이 매번 달라집니다. 그래서 LLM 설정마다 `--repeat` 로 여러 번 돌려 평균을 봅니다.
- 위 지표는 문자열과 규칙으로 계산한 근사치입니다. 사람이 읽는 것을 완전히 대신하지 못하므로 report.md 5절의 설명 원문을 몇 개는 직접 읽어 보세요.
- 설명 품질을 LLM 이 채점하는 방식(LLM judge)은 넣지 않았습니다. 채점 모델 자체의 편향이 추가되기 때문입니다.

### 5.5 결과에 따른 조정 순서

1. 검색 재현율이 낮으면: 청크 크기와 Top-K, 전략(balanced)부터 조정합니다. 검색이 놓친 근거는 프롬프트로 고칠 수 없습니다.
2. 환각 지표(phantom, cancelled as active, 근거 없는 숫자)가 남으면: 조건 문구와 few-shot 예시를 보강합니다.
3. 형식 오류로 재시도가 잦으면: JSON 모드(`--json-mode`)나 재시도 횟수를 검토합니다.
4. v2 가 v1 보다 정확도가 낮거나 비슷한데 토큰만 늘면: `EXPLAIN_PROMPT_VERSION=v1` 로 되돌리고 조건을 줄입니다.

### 5.6 실제 임베딩으로 잰 검색 결과와 적용한 개선

`python -m evaluation --phase retrieval` 을 실제 임베딩(text-embedding-3-small)으로 돌린 결과입니다. 시나리오 7개, 청크 크기 300, balanced 전략 기준이고, 숫자는 필요한 근거 묶음 중 찾은 개수입니다.

| 항목 | k=1 | k=2 | k=3 | k=5 |
| --- | --- | --- | --- | --- |
| 전용면적 | 7/7 | 7/7 | 7/7 | 7/7 |
| 소유자명 | 7/14 | 14/14 | 14/14 | 14/14 |
| 구조 유형 | 7/14 | 14/14 | 14/14 | 14/14 |
| 권리사항 | 3/5 | 5/5 | 5/5 | 5/5 |
| 건물 용도 | 7/14 | 7/14 | 7/14 | 13/14 |
| 연면적 | 0/14 | 0/14 | 7/14 | 14/14 |
| 준공년도 | 7/14 | 9/14 | 9/14 | 11/14 |

읽는 법과 적용한 것은 다음과 같습니다.

- 모든 항목에 같은 K 를 쓰면 낭비입니다. 전용면적, 소유자명, 구조 유형, 권리사항은 K=1 에서 2 면 충분하고, 건물 용도와 연면적과 준공년도만 K=5 가 필요합니다.
- 그래서 `adaptive` 전략을 추가하고 기본값으로 정했습니다. 항목별 K(`evidence.FIELD_TOP_K`)는 전용면적 1, 소유자명 2, 구조 유형 2, 권리사항 3, 건물 용도 5, 연면적 5, 준공년도 5 이고 합계 23개입니다. 항목은 서로 독립된 질의라서 각 항목의 적중은 같은 K 로 잰 값과 같으므로, 모든 항목을 K=5(35개)로 한 것과 적중은 같고 프롬프트는 약 1/3 짧습니다.
- 청크 크기는 60 이 나빴고(K=5 에서 80% 대 94~95%), 120 과 300 과 600 은 거의 같았습니다.
- balanced 는 실제 임베딩에서 효과가 작았습니다(K=3 에서 76% 대 77%). 개선의 핵심은 전략이 아니라 항목별 K 였습니다.
- 준공년도는 K=5 에서도 11/14 라서 남은 약점입니다. 검색 질의 문구를 청크 문장에 가깝게 다듬는 것이 다음 후보입니다.

## 6. 설정 값 (환경 변수)

| 이름 | 기본값 | 뜻 |
| --- | --- | --- |
| RETRIEVAL_STRATEGY | adaptive | 검색 전략 (plain, balanced, adaptive) |
| RETRIEVAL_TOP_K | 3 | 항목당 가져올 청크 수 (adaptive 에서는 FIELD_TOP_K 에 없는 항목에만 씀) |
| EXPLAIN_PROMPT_VERSION | v2 | 설명 프롬프트 버전 (v1 또는 v2) |
| LLM_TEMPERATURE | 1 | 이 모델은 1 만 허용 |
| LLM_MODEL | gpt-5.6-luna | 설명을 만드는 모델 |

## 7. 알려진 한계

- 로컬 가상환경은 langchain-core 0.3.x 이고 requirements.txt 는 0.1.x 로 고정돼 있어 둘이 다릅니다. 코드는 두 버전에 공통인 API 만 쓰고 0.1.52 에서 테스트했습니다. 0.3.x 에서는 사용자 환경의 테스트 결과로 확인이 필요합니다.
- 평가는 합성 시나리오 7개 기준입니다. 문서 하나당 청크가 4개 안팎이라 K=5 는 전체의 절반이 넘는 양을 가져오는 셈이므로, K 가 클수록 좋아 보이는 경향이 실제보다 과장됐을 수 있습니다. 실제 등기부와 건축물대장(CODEF)으로 다시 재야 일반화할 수 있습니다.
- 서버 검사는 휴리스틱입니다. 예를 들어 권리가 없는데 "근저당 채권최고액 0원"이라고 쓰는 식으로 말한 설명도 지어낸 권리로 판단해 기본 문장으로 대체합니다. 이런 오탐은 정확한 기본 문장을 쓰게 될 뿐이므로 안전한 쪽으로 틀리지만, 탈락률이 높게 나오면 설명 원문을 보고 규칙을 다듬어야 합니다.
- 항목별 K 는 위 검색 결과에서 정한 값이라, 문서 형식이 바뀌면 다시 재서 조정해야 합니다.
